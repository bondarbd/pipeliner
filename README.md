# runboard

## Что это

runboard — локальная панель для рутинных задач разработчика вида «сделать одно и то же
для N проектов, с ожиданием внешних систем и участием человека»: релиз (обновить develop →
ветка `release/0.N` → сборка в Jenkins → отчёт на Confluence), устранение уязвимости (МПР),
массовый рефакторинг, синк codestyle. Сейчас это делают bash/python-скрипты скиллов
(`~/IdeaProjects/work-skills`) под управлением gigacode из терминала.

Панель показывает эти скилы, а не заменяет их: логика по-прежнему живёт в скриптах, панель
их вызывает по описанию из YAML-шаблона, ведёт состояние на диске, рисует таблицу
«элемент × шаг» и даёт действия Retry/Skip/Abort (в UI и в CLI). Детерминированные действия — в `shell`/`js`-шагах,
LLM-агент задействуется только там, где нужен текст или суждение, и никогда не мутирует
внешние системы напрямую — каждый agent-шаг обязан иметь `verify`.

## Быстрый старт

```bash
npm install
node bin/runboard.js init
node bin/runboard.js doctor
node bin/runboard.js run hello --yes --answer Да
node bin/runboard.js serve
```

- `init` создаёт `~/.runboard/config.yaml` (0600) и `~/.runboard/templates/`.
- `doctor` проверяет окружение (node, git, agent.command, `projects_root`, `skills_root`,
  `env_file`, сами шаблоны) и печатает таблицу ✓/–/✗. На чистой машине без своих проектов
  он честно упадёт на `projects_root` (exit 1) — это нормально, поправьте путь в конфиге.
- `run hello --yes --answer Да` — первый прогон обучающего шаблона `hello` (см. «Шаблоны»).
  `--yes` подтверждает доверие шаблону при первом запуске, `--answer Да` отвечает на
  человеческий шаг без интерактивного `readline`. Шаг `gamma/flaky` в `hello` всегда падает
  и уходит в паузу — это заложено в шаблон, поэтому команда завершается кодом **2** (запуск
  `paused`), а не 0 — это ожидаемый результат первого запуска, не ошибка.
- Дальше как с любой паузой: `list` → `show <run>` (колонка info показывает причину, например
  `exit 2: permanent error: pom.xml broken`), `log <run> gamma flaky` покажет хвост лога,
  `retry <run> gamma flaky` повторит шаг (в `hello` он упадёт снова — так задумано), а
  `skip <run> gamma flaky` исключит клетку, после чего запуск доходит до `done`.
- `serve` поднимает сервер на `127.0.0.1` и печатает URL с одноразовым токеном в фрагменте
  (`#t=...`) — откройте его в браузере.

## Конфиг

`~/.runboard/config.yaml` (создаётся командой `init`, права 0700 на директорию, 0600 на файл):

```yaml
projects_root: ~/projects
skills_root: ~/.gigacode/skills          # где лежат скрипты скиллов (release/, mpr/…)
env_file: ~/.config/release/env          # секреты; в шаги попадают только по env: whitelist
agent:
  command: ["gigacode", "-p", "{prompt}", "--approval-mode", "auto-edit"]
  readonly_command: ["gigacode", "-p", "{prompt}", "--approval-mode", "plan"]
  max_parallel: 2
  timeout: 1800
limits:
  parallel: 4                # одновременных элементов на шаге
  max_attempts: 3             # на клетку (элемент × шаг)
  max_agent_calls: 30         # на запуск
  run_timeout: 21600
logs:
  retention_days: 14
  max_step_log_bytes: 5000000
```

`agent.command` — команда, которой раннер вызывает LLM-агента; раннер не знает, кто внутри.
На корп ПК это `gigacode`, локально на macOS для разработки — `claude -p ...`. Плейсхолдеры:
`{prompt}` — текст промпта (попадает в argv процесса и виден в `ps`; не подставляйте в промпт
`run.env.*`), `{prompt_file}` — путь к файлу с промптом, если агент умеет читать его из файла,
`{out}` — папка `$OUT` шага, `{ctx}` — папка контекста (`notes.md`). `agent.readonly_command` используется, когда шаг помечен `readonly: true`
(например, диагностический шаг в лестнице `on_fail`) — его точный флаг (`--approval-mode plan`
или другой) нужно проверить на корп ПК, см. чек-лист ниже.

Агент запускается с `cwd` шага (для `each` — папка проекта), а `$OUT` и `notes.md` лежат
**вне** этой папки, в `~/.runboard/runs/…`. Headless-агент с ограничением записи «только в
cwd» на попытке записать `$OUT/result` спросит разрешение, которого некому дать, и шаг
закончится `NEED_INPUT` или пустым результатом. Поэтому: (1) в промптах просите печатать
`key=value` в stdout — это всегда работает; (2) если агент умеет расширять список
разрешённых папок, передайте ему `{out}` и `{ctx}`. Пример для локальной разработки:

```yaml
agent:
  command: ["claude", "-p", "{prompt}", "--model", "haiku", "--permission-mode", "acceptEdits", "--add-dir", "{out}", "{ctx}"]
  readonly_command: ["claude", "-p", "{prompt}", "--model", "haiku", "--permission-mode", "plan"]
```

`env_file` — обычный `KEY=value`; в шаги попадают только имена из `env:` шага. В логах и
подставленных командах маскируются значения переменных, чьё имя похоже на секрет
(`*TOKEN*`, `*PASSWORD*`, `*SECRET*`, `*KEY*`, `*CREDENTIAL*`), — `DEVELOP_BRANCH=develop`
маскироваться не будет.

## Шаблоны

Шаблоны — YAML, не программа: таблица «элемент × шаг» известна до запуска, поэтому возможны
resume, retry по клетке, dry-run и валидация. Лежат в `templates/` проекта и
`~/.runboard/templates/` (при совпадении имён приоритет — у пользовательской директории).
В комплекте:

- `templates/hello.yaml` — обучающий шаблон, только локальный bash и фейковые «проекты»
  (`alpha`, `beta`, `gamma`). `beta` один раз падает и чинится через `retry`, `gamma` падает
  всегда и остаётся в паузе; барьер `succeeded` собирает сводку, пропуская `gamma`. Это
  первое, что стоит запустить — он же smoke-тест панели.
- `templates/debts.yaml` — разбор очереди долгов (см. «Очереди долгов и доска»), без агента.
- `templates/release.yaml` — реальный релиз на скриптах скилла `release`
  (`git_release.sh`, `jenkins.py`, `confluence_check.sh`). Шаг `publish` рассчитывает на MCP
  Confluence у агента; без него агент честно ответит `NEED_INPUT`, и шаг останется ждать.

Шаблон снимается в `run.json` при старте: правка YAML не влияет на уже идущий запуск (в том
числе на `retry` его клеток) — для нового текста нужен новый запуск.

### Параметры и элементы

```yaml
params:
  release: { type: string, required: true, label: "Номер релиза", pattern: "^[0-9]+$" }
  version: { type: string, default: "1.12.0" }     # default подставляется, если параметр не передан
items:
  source: dirs        # элементы — подпапки projects_root; передаются через --items a,b (обязательно)
  # source: manual    # элементы — объекты с полем name: default: [...] в шаблоне, --items a,b или JSON в UI
  # source: queue, queue: debts   # открытые элементы очереди ~/.runboard/inbox/debts (см. ниже)
```

Пример шага с идемпотентностью: `check` — это команда, важен только её код возврата
(0 = «уже сделано, тело не запускать»), stdout `check` при этом становится результатом шага:

```yaml
- name: bump
  each: true
  check: git -C "${{ item.dir }}" rev-parse --verify -q feature/bump-commons-text
  shell: git -C "${{ item.dir }}" checkout -b feature/bump-commons-text && sed -i '' 's#<version>1.9</version>#<version>${{ run.params.version }}</version>#' "${{ item.dir }}/pom.xml" && git -C "${{ item.dir }}" commit -qam "bump commons-text"
  verify: grep -q "<version>${{ run.params.version }}</version>" "${{ item.dir }}/pom.xml"
```

### Поля шага (§4.2)

| Поле | Значение |
|---|---|
| `name` | уникальное имя, латиница |
| `each: true` / `once: true` | ровно одно из двух |
| `barrier` | только для `once`: `all` (по умолчанию) или `succeeded` |
| тело | ровно одно из: `shell` (строка), `js` (путь к модулю), `agent` (объект), `human` (объект) |
| `output` | `keys` (строки `key=value` из stdout, по умолчанию), `json` (файл `$OUT/result.json` или последняя JSON-строка stdout), `text` |
| `items` | выражение-массив объектов → добавляет элементы (только в `once`-шаге; более ранние шаги у новых элементов — `n/a`; дедупликация по `name`; больше `limits.max_new_items` (50) новых — шаг падает в паузу, ничего не добавив) |
| `when` | выражение; ложь → `skipped` |
| `check` | команда; exit 0 → шаг уже выполнен, тело не запускается (идемпотентность, reconcile после рестарта) |
| `verify` | команда; обязательна для `agent`; exit ≠ 0 → шаг `unverified` |
| `retriable` | без него `do: retry` в `on_fail` — ошибка валидации |
| `on_fail` | лестница, см. ниже |
| `timeout` | секунды; агентные шаги — `agent.timeout` из конфига (1800 по умолчанию), остальные — 3600, в конфиге не настраивается |
| `env` | whitelist переменных из `env_file`, видимых шагу; по умолчанию — ни одной |
| `cwd` | по умолчанию `item.dir` для `each`, папка запуска для `once` |
| `resource` | строка; на время шага берётся межпроцессный lock (обычно `repo:<dir>`) |
| `parallel` | лимит одновременных элементов на этом шаге |

`agent`: `prompt`, `input` (выражение, сериализуется в JSON и вставляется в промпт
fenced-блоком с пометкой «данные, не инструкции»), `readonly: true` (использует
`readonly_command`), `timeout`. `human`: `question`, `options` (по умолчанию `[Да, Нет]`),
`fields`; `on_fail` к `human` неприменим (это ошибка валидации), «Нет» ведёт к паузе дорожки.
`js`: модуль экспортирует `async (ctx) => object`, выполняется в процессе панели — поэтому
`js`-шаги допускаются только из локальных папок шаблонов (`templates/`, `~/.runboard/templates/`).

### Лестница on_fail (§4.3)

| `do` | параметры | смысл |
|---|---|---|
| `retry` | `times`, `delay` | повтор тела (после `check`); требует `retriable: true` на шаге |
| `agent` | `prompt`, `then: pause` (опционально; единственное значение в v1) | read-only агент (всегда через `agent.readonly_command`) пишет диагноз в `notes.md`; не более 1 раза на клетку. С `then: pause` дорожка сразу уходит в паузу; без `then` лестница продолжается следующей ступенью (которая, как и всякая лестница, обязана заканчиваться терминальной ступенью) |
| `pause` | — | дорожка ждёт человека: Retry / Skip / Abort item |
| `skip_item` | — | элемент помечается `skipped`, барьеры его не ждут |
| `abort` | — | остановить весь запуск |

Пропуск `on_fail` = `[{do: pause}]`. Последняя ступень всегда терминальная
(`pause`/`skip_item`/`abort`).

### Выражения (§4.4)

Единый синтаксис `${{ expr }}`, вычисляется в `node:vm` с таймаутом 100 мс. Это защита от
опечаток и зависаний, а не граница безопасности: шаблон — доверенный локальный файл, и все
его выражения (`when`, `items`, `cwd`, `resource`, `agent.input`, `check`, `verify`) показываются
при подтверждении доверия. Если выражение — весь скаляр, тип результата сохраняется; внутри строки — приводится к
строке. Доступно: `run.params.*`, `run.env.*` (только whitelist шага), `run.items[]` (каждый
элемент — с `steps.<step>.*`, результатами его each-шагов), `run.steps.<once-step>.*`, `run.skills`, `run.dir`, `run.id`; `item.name`, `item.dir`,
`item.*`, `item.steps.<step>.*`, `item.ctx`; `output` — только в `items:`.

При подстановке в `shell` каждое значение проверяется регуляркой
`^[A-Za-z0-9._/@:=+, -]*$` — иначе шаг падает с `unsafe substitution` ещё на этапе рендера
(защита от инъекции через имена веток/тикетов). Для осознанных исключений — `raw: true` на
шаге, помечается в UI.

### Доверие шаблонам (trust-on-first-use)

Хеш шаблона считается по YAML-файлу и всем связанным файлам (`js:`-пути, всё под
`templates/<name>/`). При первом запуске нового или изменённого шаблона панель показывает
список его команд после подстановки и требует подтверждения: в CLI — флаг `--yes`, в UI —
кнопка «Подтвердить». После подтверждения хеш запоминается, повторные запуски того же
содержимого проходят без вопроса.

## Очереди долгов и доска

Помимо конечных задач есть открытые долги без конца: ответить человеку в чате, переслать
известное, выполнить своё обещание. Для них есть очереди: плоские JSON-файлы в
`~/.runboard/inbox/<queue>/`, которые движок не читает сам. Захват стоит одну строку:

```bash
runboard add debts "Петя: где дистрибутив 0.247?" --link "sberchat://…"   # или текст из stdin: add debts -
runboard queue                # открытые и отложенные элементы всех очередей
runboard board                # что требует меня сейчас: паузы, вопросы, просроченные долги (--all: всё живое)
```

Разбор долгов это обычный запуск шаблона `debts` (`items: { source: queue, queue: debts }`):
каждый открытый элемент становится элементом запуска, шаг `reply` задаёт вопрос с кнопками
«Отправил / Завтра / Понедельник / Через неделю / Не нужно», шаг `close` закрывает или
откладывает элемент в очереди. Отправляет всегда человек, панель фиксирует факт. Третье
откладывание закрывает элемент само, чтобы список не зарастал. Без агента: шаблон работает
на машине без настроенного `gigacode`.

Утренний запуск ставится в cron ОС, встроенного планировщика нет:

```
45 8 * * 1-5  cd /path/to/runboard && RUNBOARD_HOME=$HOME/.runboard node bin/runboard.js run debts --yes >> $HOME/.runboard/cron.log 2>&1
```

Без терминала команда остановится на первом human-шаге (код 2), запуск останется
`waiting_for_human`, и утром он виден на доске (`runboard board` или экран «Доска» в UI,
где сверху поле захвата, а у элементов со ссылкой кнопка «Открыть»). Если `serve` поднят,
cron-команда уйдёт через его API. Первый запуск требует доверия шаблону: сделайте его один раз
руками с `--yes`, иначе cron-запуск завершится кодом 3.

Открытый элемент очереди это ещё не «требует меня»: до утреннего запуска он виден в
`runboard queue` и `board --all`, а на доске без флага появляется, когда его human-шаг ждёт
ответа или когда просрочен отложенный срок. Ответ на human-шаг с кнопками принимается только
из списка кнопок, иначе `answer` вернёт ошибку и ничего не изменит. Если шаг `close` всё же
ушёл в паузу (например, элемент удалили из очереди руками), `runboard skip <run> <id> close`
завершит запуск, а элемент, если он ещё открыт, подберёт следующий утренний запуск.

Правило `outbound: true` на шаге `shell`/`js`/`agent`, который пишет людям (комментарий в
Jira, письмо, сообщение): такой шаг обязан идти сразу после `human`-шага того же вида, и
движок запускает его только при утвердительном ответе («Да», «Отправить», «Подтверждаю»),
иначе клетка получает `skipped` с причиной `outbound: not confirmed`. Пометка видна в списке
команд при доверии шаблону. Чтобы «Нет» сразу вело к пропуску, а не к паузе дорожки, задайте
у human-шага `pause_on: []` (иначе «Нет» по умолчанию ставит паузу, и понадобится `skip`).

`human.pause_on: []` означает «ни один ответ не ставит дорожку на паузу» (по умолчанию
паузу вызывают «Нет»/«No»).

## Контекст запуска

```
runs/<id>/
  run.json
  context/run.md               # цель, параметры, решения человека
  context/steps/<step>.json    # output once-шагов (+ файлы из $OUT рядом)
  items/<name>/context/notes.md          # свободный текст: агент и человек
  items/<name>/context/steps/<step>.json # output шага
  items/<name>/logs/<step>.<seq>.log     # сырой вывод, seq — сквозной
  items/<name>/logs/<step>.<seq>.diff    # после agent-шага
```

Агент в шапке промпта получает путь `CTX_ITEM`, содержимое `notes.md` (хвост 8 КБ, внутри
делимитера «данные»), результаты предыдущих шагов элемента (JSON) и инструкцию: результат —
в `$OUT/result.json` или строками `key=value`; свои выводы дописывать в `notes.md`; вопросов
не задавать — если нужен ответ человека, завершить работу строкой `NEED_INPUT=<вопрос>`.
`NEED_INPUT` панель превращает в `human`-шаг, ответ дописывается в `notes.md`, шаг
повторяется. После трёх `NEED_INPUT` подряд на одной клетке она уходит в паузу (агент
явно не может продолжить — нужен человек, `retry` сбрасывает счётчик). `notes.md` можно
редактировать из UI (подсказка агенту перед retry). Строки `key=value` распознаются и в
markdown-обёртке (`**key=value**`, `` - `key=value` ``), что прощает слабым моделям оформление.

## CLI

```
runboard init                                        создать ~/.runboard/config.yaml и templates/
runboard doctor                                       проверить окружение (node, git, agent, projects_root, skills_root, env_file, шаблоны)
runboard validate <template>                          проверить YAML шаблона
runboard render <template> --step S [--item I]        показать подставленную команду шага, без запуска
runboard run <template> --param k=v --items a,b --mode all|pilot [--dry-run] [--yes] [--answer TEXT]
runboard list                                         список запусков
runboard show <run>                                   таблица элемент × шаг для запуска
runboard log <run> <item|_> <step> [--kind K] [--seq N]     хвост лога клетки: последней попытки или попытки N (K: log|check|verify|diagnose|diff)
runboard retry <run> <item|_> <step>                  повторить клетку (_ — once-шаг)
runboard skip <run> <item|_> <step>                   пропустить клетку (барьеры её не ждут)
runboard abort <run> [item]                           прервать запуск целиком или исключить один элемент
runboard answer <run> <item|_|__pilot__> <step|-> TEXT [--wait N]   ответить на human-шаг, вопрос агента или пилота
runboard board [--all]                                доска: что требует меня сейчас (или всё живое)
runboard add <queue> <text…|-> [--link URL]           захватить долг в очередь
runboard queue [name]                                 открытые и отложенные элементы очередей
runboard done|drop <queue> <id>                       закрыть элемент; snooze <queue> <id> [tomorrow|monday|week|YYYY-MM-DD]
runboard clean [--days N]                              удалить старые запуски (retention_days по умолчанию)
runboard serve [--port P]                              поднять сервер на 127.0.0.1, напечатать URL с токеном
```

Клетка once-шага не привязана к элементу: в CLI на месте элемента пишется `_` (или `*`), в
API — `"_"`, в `run.json` такие клетки лежат в `once`, а не в `cells`. В таблице `show`
статус `success ×2` означает, что шаг прошёл со второй попытки (автоповтор лестницы);
логи прошлых попыток лежат рядом, `log … --seq N` покажет нужную.

`run`/`retry`/`skip`/`answer` без сервера выполняют движок прямо в этом процессе и ждут, пока
запуск не остановится: `done`, пауза или вопрос человеку. Вопрос задаётся в терминале;
`--answer TEXT` отвечает им заранее (на human-шаги и на вопрос пилота, но **не** на
`NEED_INPUT` агента — там нужен осмысленный ответ). Без терминала (cron, CI, пайп) команда не
ждёт ввода, а печатает вопрос и готовую команду `runboard answer …` и завершается кодом 2.

`--dry-run` показывает подставленные команды всех клеток без запуска; результаты ещё не
выполненных шагов выводятся плейсхолдерами: `${{ item.steps.branch.commit }}` → `@branch.commit`.

Если `runboard serve` уже запущен, команды `run`/`retry`/`skip`/`abort`/`answer`/`clean` идут
через его API (не создают второй движок); иначе выполняются в собственном процессе под
instance lock'ом, чтобы не пересекаться с работающим сервером. Команда в собственном процессе
трогает только тот запуск, о котором её спросили: остальные незавершённые запуски лежат на
диске как есть, пока их не продолжит `serve` или команда по ним.

После аварийного завершения панели (kill -9, перезагрузка) клетки, которые в этот момент
выполнялись, становятся `interrupted`, а pid их процесса сохраняется как `orphanPid` в
`run.json`. Панель не убивает такие процессы сама (после перезагрузки pid может принадлежать
чужому процессу); проверьте их руками, затем `retry` — если у шага есть `check`, он сам
определит, что работа уже сделана.

Коды возврата `run`/`retry`/`skip`/`abort`/`answer`: **0** — запуск дошёл до `done`; **2** —
запуск остановился, не дойдя до `done` (пауза, вопрос человеку, `aborted`); **1** — ошибка
самой команды (не найден шаблон/запуск, неверные параметры); **3** — шаблон не прошёл
проверку доверия и нужен `--yes`. `show`, `list`, `log` возвращают 0: они показывают состояние,
а не оценивают его.

### HTTP API

Все запросы — с заголовком `X-Runboard-Token: <токен из ~/.runboard/token>`, `Host` должен быть
`127.0.0.1:<port>`. Тела — JSON. Действия возвращают `204`, ошибки — `{ "error": "…" }`.

| Метод и путь | Назначение |
|---|---|
| `GET /api/templates` | шаблоны с параметрами, `hash` и флагом `trusted` |
| `POST /api/templates/:name/trust` `{hash}` | подтвердить доверие |
| `POST /api/templates/:name/preview` `{params, items}` | то же, что `--dry-run` |
| `GET /api/projects` | подпапки `projects_root` (git-репозитории или maven-модули) |
| `GET /api/runs`, `GET /api/runs/:id` | список запусков; полный `run.json` |
| `POST /api/runs` `{template, params, items, mode}` | создать запуск → `201 {id}`; `409 {needsTrust, hash, commands}` если шаблон не подтверждён |
| `GET /api/runs/:id/log?item=<name|_>&step=S&seq=N[&kind=K][&bytes=N]` | хвост лога клетки (`seq` — из `run.json`) |
| `GET/PUT /api/runs/:id/context?item=<name|_>` | `notes.md` (+ `notesHash`) и результаты шагов; `PUT {notes, notesHash}` перезаписывает заметки, `409` если файл изменился с момента чтения |
| `POST /api/clean` `{days}` | удалить завершённые запуски старше `days` (по умолчанию `retention_days`) |
| `POST /api/runs/:id/render` `{item, step}` | подставленная команда клетки живого запуска |
| `POST /api/runs/:id/cells/:item/:step/retry` · `/skip` | действия над клеткой (`_` — once-шаг) |
| `POST /api/runs/:id/items/:item/abort` | исключить элемент |
| `POST /api/runs/:id/answer` `{item, step, answer, fields}` | ответ на human-шаг или `NEED_INPUT`; пилот: `item: "__pilot__", step: null` |
| `POST /api/runs/:id/pause` · `/resume` · `/abort` | пауза/продолжение/прерывание запуска |
| `GET /api/board[?all=1]` | строки доски: `{kind, group, item, step, state, info, age, link, runId, needsMe}` |
| `GET /api/queues[?all=1]` · `POST /api/queues/:name` `{text, link}` | открытые и отложенные элементы (`all=1` — с закрытыми); захват → `201` с элементом |
| `POST /api/queues/:name/:id/done` · `/drop` · `/snooze` `{when}` | закрыть или отложить элемент |

## Чек-лист перед запуском на корп ПК

Проверить до реализации/использования agent-раннера на корп ПК:

1. `gigacode --help`: точное имя флага headless (`-p`), значения `--approval-mode` (есть ли
   read-only/plan), флаг таймаута/лимита ходов, есть ли resume-сессии (не используем, но
   знать).
2. Поведение при параллельном запуске 2–3 процессов из разных cwd: нет ли общего
   lock/сессии в `~/.gigacode/`.
3. Что выводится в stdout в headless-режиме: только ответ или ещё лог tool-calls (влияет на
   `output: keys`).
4. Работает ли MCP (confluence) в headless-режиме без интерактивного подтверждения при
   `auto-edit`.

Результаты вносятся в `config.yaml` и, при необходимости, в
`docs/superpowers/specs/2026-09-18-runboard-design.md`.

Практические команды для проверки пп. 1–3:

```bash
gigacode --help
gigacode -p "напечатай OK" --approval-mode auto-edit
```

Запустить последнюю команду параллельно из двух разных папок проектов и убедиться, что в
stdout — только ответ агента (а не вперемешку с логом инструментов) и что процессы не мешают
друг другу через общее состояние в `~/.gigacode/`. По итогам заполнить в
`~/.runboard/config.yaml` точный `agent.readonly_command` (флаг read-only/plan режима,
найденный на шаге 1).

`skills_root` в конфиге должен указывать на директорию, СОДЕРЖАЩУЮ `release/` со скриптами
скилла (`git_release.sh`, `jenkins.py`, `confluence_check.sh`) — на корп ПК это
`~/.gigacode/skills`. Настройки самих скриптов (Jenkins, Confluence) читаются из
`env_file` (по умолчанию `~/.config/release/env`, права 0600) — см. пример переменных,
включая `CONFLUENCE_URL`, `CONFLUENCE_TOKEN`/`CONFLUENCE_USER`/`CONFLUENCE_PASSWORD`,
`CONFLUENCE_SPACE`, `CONFLUENCE_RELEASE_TITLE`, в
`~/IdeaProjects/work-skills/release/config.example.env`.

Шаг `build` в `templates/release.yaml` вызывает `jenkins.py run-one` с явным `--max-retries 0`
(ретраи владеет только лестница runboard, `on_fail: retry times 1`) и передаёт в шаг
`RUN_ONE_MAX_WAIT` (ожидание сборки в jenkins.py, по умолчанию 5400с) при `timeout: 6600` самого
шага runboard — таймаут шага должен оставаться больше `RUN_ONE_MAX_WAIT`.

## Безопасность

- Сервер слушает только `127.0.0.1`; токен в `~/.runboard/token` (0600) передаётся UI один
  раз через URL (`/#t=...`), дальше хранится в `sessionStorage` и шлётся заголовком
  `X-Runboard-Token`; проверяются `Origin` и `Host` запроса.
- Шаблоны и `js`-шаги — только из `templates/` проекта и `~/.runboard/templates/`; первый
  запуск нового/изменённого шаблона требует подтверждения (см. «Доверие шаблонам» выше).
- Секреты из `env_file` попадают в шаг только по `env:`-whitelist, никогда не в argv;
  маскируются при записи в лог, промпты и подставленные команды (точное значение, base64 и
  urlencoded формы, плюс `Authorization:`, `token=`, `password=`) — маскирование снижает шум,
  а не гарантирует отсутствие утечки.
- Подстановки в `shell` отклоняются при небезопасных символах (`unsafe substitution`) ещё до
  запуска — защита от инъекции через имена веток/тикетов.
- git-обёртка отклоняет команды с `--force`; push разрешён только в ветки по паттерну из
  конфига (`release/*`, `feature/*`) — эта проверка по тексту команды, best effort, настоящая
  защита — branch protection на сервере.

## Чего нет в v1

Свой MCP-клиент; `goto`; `{{#each}}` и mustache; шаги `poll`, `http`, вложенные
шаблоны-подзапуски, form-builder для элементов (есть `manual` через JSON в textarea);
event-sourcing и SSE; планировщик; мультипользовательность; OS keychain; отдельный worktree
на запуск; вложенный `each` (при необходимости — `js`-шаг, возвращающий массив элементов).
